**1. What should count as a failure worth retrying?** Today only a connection-level failure throws, so a supplier answering `503` is retried zero times and recorded as success (`src/jobs/sync.ts:5`). Backoff is meaningless until something fails.
- **a) The call site checks the response and throws on a retryable status** — `syncCatalog` inspects `res`, throws for statuses worth retrying, and lets the rest return. The cost is that `syncCatalog` grows the HTTP knowledge, and `withRetry` stays a dumb loop that retries anything thrown. **Recommended**: it puts the protocol decision next to the only code that speaks the protocol, and it needs no new parameter on the helper.
- **b) `withRetry` gains a `shouldRetry(error)` predicate the caller passes** — the retry policy becomes the helper's business and is reusable by the next caller. The cost is a new parameter and a second decision (Q5-style configurability) forced immediately, for a helper with one caller.
- **c) Leave failure detection alone** — only connection errors retry. The cost is that the 503 path keeps reporting a broken sync as a success, and this plan does not address the problem it was written for.

**2. What should the attempt cap be, now that it is 5?** Your "keep as is" was a decision about 3. At five attempts there are four gaps; at a 500 ms base doubling each time, the helper sleeps 0.5 + 1 + 2 + 4 = **7.5 s** before giving up, where a three-attempt version would sleep 1.5 s.
- **a) Keep 5** — unchanged behaviour on the attempt axis, and the best tolerance of a short outage. The cost is the 7.5 s figure above, which grows with whatever Q3 picks. **Recommended**: the cap was never the defect — immediacy was — and this is a background sync job where seven seconds costs nothing.
- **b) Reduce to 3** — the job fails fast, sleeping about 1.5 s. The cost is giving up on outages that 5 attempts would have ridden out, to buy back seconds nobody is waiting on.

**3. The backoff profile.** These three cannot be settled separately — together they are the delay schedule — so answer all three. Figures below assume the current cap of 5 attempts, i.e. four gaps; they shrink if Q2 picks (b).
- **3a) Base delay — 200 ms / 500 ms / 1 s.** Doubling, the total sleep is 3.0 s, 7.5 s or 15 s respectively. **Recommended: 500 ms** — long enough that the second attempt is not effectively immediate, short enough that the common case (one transient blip) resolves in half a second.
- **3b) Multiplier — 2 or 3.** At a 500 ms base, doubling totals 7.5 s and the last gap is 4 s; tripling totals 20 s and the last gap is 13.5 s. **Recommended: 2** — tripling buys a longer final wait that an unreachable supplier is unlikely to recover inside anyway, and it makes the job's worst case harder to reason about.
- **3c) Jitter — none, or full jitter (each delay a random value in `[0, computed]`).** Jitter exists to stop many clients retrying in lockstep. This job has one call site, invoked once per run, retrying sequentially in one process — there is no fleet to de-synchronise. **Recommended: none** — it adds randomness to a schedule whose determinism is what makes it testable, and buys a benefit that needs concurrent contending clients to exist.

**4. Should there be a maximum total delay cap?** The topic floats one. With a fixed attempt cap and a fixed multiplier, the total *sleep* is already a constant you can compute — 7.5 s under the recommendations above — and finding 4 means a cap would not bound the job's runtime, because the attempts themselves are untimed.
- **a) No separate cap** — the attempt count and the multiplier bound the sleeping, and Q5 bounds the waiting. The cost is that if you later add jitter or raise the cap, nobody is forced to re-check the total. **Recommended**: a knob that can never fire is a knob that will be misread as protection it does not give.
- **b) An explicit total-delay budget** — one number states the intent directly and survives later changes to the base or cap. The cost is a second mechanism that duplicates what the attempt cap already decides, and an extra branch to test.

**5. Should each attempt get its own timeout?** Not in the topic, and it is the only change that delivers "a sync job cannot hang for minutes": there is no `AbortSignal` anywhere today, so one connection that opens and then stalls blocks the job indefinitely, with or without backoff.
- **a) Pass a per-attempt timeout to `fetch`** — e.g. `AbortSignal.timeout(10_000)` at `src/jobs/sync.ts:5`. A stall becomes an abort, which throws, which retries. Worst case becomes bounded: five attempts of at most 10 s plus 7.5 s of sleep, about 58 s. The cost is one more number to pick and the risk of aborting a slow-but-healthy large response. **Recommended**: without it, every other bound in this plan is decorative.
- **b) Leave it out and defer** — smaller change, and the backoff work ships alone. The cost is shipping a plan whose stated goal — not hanging for minutes — remains unmet; if you take this, it needs a named owner rather than a note.

**6. Hand-roll the backoff, or adopt a retry library?** This repository has zero dependencies and no lockfile, so either way this is its first one.
- **a) Hand-roll** — roughly ten lines inside the existing loop: a sleep before each retry after the first. The cost is implementing the predicate and any future jitter yourself. **Recommended**: the helper is 13 lines and has one caller; a dependency plus a lockfile plus an install step is a larger change to this repository than the feature is.
- **b) Adopt a retry library (`p-retry` or similar)** — backoff, jitter and a retry predicate arrive tested. The cost is the repository's first runtime dependency, a lockfile, and an install story it does not have yet; it also pre-answers the configurability question, since the policy then lives at the call site.

**7. How should this be tested?** `npm test` fails today because `vitest` is named in `package.json:6` but declared nowhere, and there are no test files — so the timing change would ship with nothing checking it.
- **a) Declare `vitest` and write timing tests with fake timers** — assert the attempt count and the exact delay sequence. The cost is making the repository installable (a devDependency plus a lockfile) as part of this work. **Recommended**: a deterministic schedule (3c = none) is cheap to assert exactly, and without a test the delay profile is unverifiable by inspection.
- **b) Verify by hand and leave the test script broken** — nothing extra to set up. The cost is that every future change to these numbers is a guess.
- **c) Fix the test setup as separate work first** — keeps this change small, at the price of the backoff landing untested in the meantime.
