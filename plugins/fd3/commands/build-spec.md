---
description: "Build a spec for a topic, plan, decision or idea by grilling it round by round, then writing it up and validating it."
argument-hint: "<topic, plan, decision or idea to grill — e.g. \"our retry strategy\" or path/to/PLAN.md>"
---

Three stages, in order. The grilling runs here, in the main thread — it needs the user. The writing and the validation run in their own contexts, so their reading never fills this conversation: relay each report, never re-derive or expand it — with one exception: where a report contradicts something you told the user, say so in the open, name both and which one now stands.

**A finished spec re-enters at stage 3.** When `$ARGUMENTS` is a path to an existing file that carries the template's `## 12. Appendix — the evidence record` section (`${CLAUDE_PLUGIN_ROOT}/references/spec-template.md`), it is a spec coming back for validation — edited after its verdict, or stale against its repositories. Grilling it again would re-open decisions the user already made: skip stages 1 and 2 and run stage 3 on that path. The first pass's focus list is what changed since the last verdict line — the sections its line count no longer covers, the sections `git log` shows edited since the commit that wrote it — plus any drift the user or the calling skill named. Everything else in the stage-3 loop applies unchanged.

1. Invoke the `fd3:grill-topic` skill with `$ARGUMENTS`, forwarded verbatim. Work its rounds to the end. While its lookups run, speak only when there is something to decide — a round ready to post, a returning fact that voids a question already asked, or a command the user must run; a lookup that came back and changed nothing gets one line.
2. Once the user confirms the closing summary — and not before — invoke the `fd3:write-spec` skill with the path of the closing-notes file the grilling wrote, the session's research directory, and where the spec goes. The paths, never a description of where things are. Where the spec goes is a path in the repository the work lands in, following the layout its existing specs or design docs already use; when the repository has no such layout, that location is a question in the closing round. Never default it to the scratchpad: a spec that lives there has to be moved later, and the move rewrites the document after its verdict. It runs in its own context; do not wrap it in a sub-agent of your own. Relay its report: where the spec went, the counts, what is not yet settled in it, and the question batch it closes with — asked the same way, with the answers sent back to it with `SendMessage` so it applies them before validation starts. If it stops to ask instead, put its questions to the user here, batched per `${CLAUDE_PLUGIN_ROOT}/references/question-batching.md` and asked through `AskUserQuestion`, and send the answers back with `SendMessage` — it resumes where it stopped. Relaying them in prose invites answers you have to interpret; where a question has sub-parts, number them (`20.1`, `20.2`) rather than lettering them beside lettered options.
3. Then invoke the `fd3:validate-spec` skill on the written spec. It runs in its own context and returns its verdict and status. Validation is also where the spec's defects get repaired: the skill edits the spec wherever a fact settles one, so its report lists spec edits alongside findings. A verdict on a spec that had findings and lists no edits is a pass that only counted them — say so when you relay it. Invoke it again on the same spec, passing back the status it returned, while either holds: the verdict is not ready and a further pass could close what remains, or the pass applied spec edits — a `ready` verdict on a document the same pass rewrote is a verdict on the version before those edits, and nothing but the next pass ever reads them. At most three passes in all, and say plainly what is still open if the third ends short. Each re-invocation carries a **focus list** alongside the status: the findings the previous pass left open and the sections it edited. That is what the next pass spends itself on; everything the status records as verified it inherits. A pass that stopped to ask is not finished: resume it with `SendMessage`, never with a fresh invocation. A pass that ended its own turn with a verdict is finished, and the next invocation is a fresh reading of a document the previous pass edited — the only thing that ever re-checks those edits, so do not skip it because the verdict looks close. If it stops to ask instead, put its questions to the user here, batched per `${CLAUDE_PLUGIN_ROOT}/references/question-batching.md`, and send the answers back with `SendMessage` — it resumes where it stopped. Relay the final verdict, and relay every finding the status leaves standing inside a passing check.

The final verdict describes the file as the last pass left it, and its line count is how the next stage checks that. Any change to the spec after it — a tickets table, a move to another path, a rewritten header, a corrected link — is an edit no pass has read: run one more pass focused on exactly those edits, outside the three-pass cap, before you call the spec done. The status, the verdict and any "validated" wording are written by passes only; never type them into the spec yourself.

Confirmation of shared understanding is the gate between stages 1 and 2. If the user ends the session without confirming, stop after the first stage and say what is still open.
