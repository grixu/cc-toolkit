code-review runs one reviewer per lens over your change, all in parallel, and merges what they find into one report grouped by file.
Every finding names its rule and gets its severity from one fixed table, so two runs over the same change are comparable.
After the report, one menu asks which fixes to apply and how to commit them.
Nothing is edited until you choose.

## When to reach for it

- **Before you open a pull request.** The agent reads its own branch the way a reviewer would, and fixes what it can before a person spends time on it.
- **On a change made outside fd3.** [`/fd3:implement`](/plugins/fd3/implement/) already reviews every branch it builds, through the same lenses.
- **On someone else's pull request.** The review drafts comments for the author instead of editing their branch.

Claude Code's bundled `/code-review` skill shares the plugin's name.
It is a single bug-hunting pass; this plugin grades every finding against a written rule.

## What's in the plugin

| Part | Who runs it | What it does |
|---|---|---|
| [`/code-review:start-cr`](/plugins/code-review/start-cr/) | you | Reviews a branch, a set of paths or a pull request, then offers the apply menu. |
| `scanner` agent | `start-cr` and workflows | Judges the change against one lens's rules and writes that lens's findings to a file. |
| `cr-prepare`, `cr-scan`, `cr-merge` | workflows such as `/fd3:implement` | The same review split into headless steps that ask nothing and edit nothing. |

Table 1. The parts of code-review

You only run `start-cr`.
The headless skills are hidden from the `/` menu; the [reference](/plugins/code-review/reference/#headless-steps) lists their arguments for workflow authors.

## Requirements

- `git`: the change is read from git.
- `python3`: a bundled script finds the changed files and the base branch.
- The `Agent` tool in your session: each lens runs as its own sub-agent.
- `gh`, only to review a GitHub pull request.
